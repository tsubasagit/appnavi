# CRMテンプレート仕様書（月額1000円相当版）

## 1. 概要

本仕様書は、AppNaviのCRMテンプレートを**月額1000円を払う価値がある**レベルに引き上げるための詳細仕様です。

### 1.1 目標
- IT経営者100人が「これなら1000円/月払ってもいい」と判断できる品質
- 実際の業務で即座に使える完成度
- 他社CRMツール（無料版）を超える実用性

### 1.2 評価基準
以下の3つの観点で評価：
1. **方針（Policy）**: データ構造の設計思想と実用性
2. **デザイン**: UI/UXの完成度と使いやすさ
3. **サンプルデータ**: リアリティと量の十分性

---

## 2. 方針（Policy）仕様

### 2.1 データ構造の設計思想

#### 2.1.1 必須データソース（3つのシート）

**1. 顧客マスタ（customers）**
- **目的**: 顧客の基本情報を一元管理
- **特徴**: 1顧客 = 1行のシンプル構造
- **更新頻度**: 中（新規登録・情報更新時）

**2. 商談管理（deals）**
- **目的**: 商談の進捗と金額を管理
- **特徴**: 1商談 = 1行、顧客IDで顧客マスタと紐付け
- **更新頻度**: 高（商談ステージ変更時）

**3. 活動履歴（activities）**
- **目的**: 顧客への接触履歴を時系列で記録
- **特徴**: 1活動 = 1行、顧客IDで顧客マスタと紐付け
- **更新頻度**: 高（電話・メール・訪問の都度）

#### 2.1.2 データソース間の関係性

```
customers (1) ──< (N) deals
customers (1) ──< (N) activities
```

- **1対多の関係**: 1顧客に対して複数の商談・活動履歴が存在
- **紐付け方法**: `顧客ID`カラムで関連付け
- **整合性**: 顧客IDは必ず顧客マスタに存在する必要がある

### 2.2 各データソースの詳細仕様

#### 2.2.1 顧客マスタ（customers）

| カラム名 | 型 | 必須 | 説明 | 例 | 備考 |
|---------|-----|------|------|-----|------|

| 顧客名 | string | ✅ | 担当者名または代表者名 | `山田太郎` | 検索対象 |
| 会社名 | string | ✅ | 法人名または個人事業主名 | `株式会社サンプル` | 検索対象 |
| 部署名 | string | ❌ | 所属部署 | `営業部` | |
| 役職 | string | ❌ | 役職名 | `部長` | |
| メールアドレス | string | ❌ | 連絡先メール | `yamada@example.com` | バリデーション必要 |
| 電話番号 | string | ❌ | 連絡先電話 | `03-1234-5678` | ハイフン有無どちらでも可 |
| 郵便番号 | string | ❌ | 郵便番号 | `100-0001` | |
| 住所 | string | ❌ | 都道府県+市区町村+番地 | `東京都千代田区千代田1-1` | |
| 業種 | string | ❌ | 業種分類 | `IT・ソフトウェア` | 選択肢推奨 |
| 従業員数 | number | ❌ | 従業員数 | `50` | |
| 年商 | number | ❌ | 年間売上高（万円） | `50000` | |
| 顧客ステータス | string | ✅ | 顧客の状態 | `見込み` | 選択肢必須（後述） |
| 見込み度 | string | ❌ | 成約見込み度 | `高` | 選択肢必須（後述） |

| 最終接触日 | date | ❌ | 最後に連絡した日付 | `2024-01-15` | 自動更新推奨 |
| 登録日 | date | ✅ | 顧客登録日 | `2024-01-01` | 自動設定 |
| 備考 | string | ❌ | 自由記述のメモ | `来月に再度訪問予定` | |

**顧客ステータスの選択肢**:
- `見込み`: まだ成約していない見込み客
- `商談中`: 現在商談が進行中
- `既存顧客`: 既に成約済みの顧客
- `休眠`: 長期間連絡が取れない
- `失注`: 成約に至らなかった

**見込み度の選択肢**:
- `高`: 成約確率70%以上
- `中`: 成約確率30-70%
- `低`: 成約確率30%未満

#### 2.2.2 商談管理（deals）

| カラム名 | 型 | 必須 | 説明 | 例 | 備考 |
|---------|-----|------|------|-----|------|
| 商談ID | string | ✅ | 一意の識別子（自動生成推奨） | `DEAL-001` | |
| 顧客ID | string | ✅ | 顧客マスタの顧客ID | `CUST-001` | 外部キー |
| 商談名 | string | ✅ | 商談の名称 | `新規システム導入案件` | |
| 商談金額 | number | ✅ | 見積金額（円） | `5000000` | 0以上の数値 |
| 商談ステージ | string | ✅ | 商談の進行段階 | `提案中` | 選択肢必須（後述） |
| 見込み度 | number | ❌ | 成約確率（%） | `70` | 0-100の数値 |
| 見込み成約日 | date | ❌ | 成約予定日 | `2024-03-31` | |
| 担当者 | string | ❌ | 自社の担当者名 | `佐藤花子` | |
| 開始日 | date | ✅ | 商談開始日 | `2024-01-10` | |
| 更新日 | date | ✅ | 最終更新日 | `2024-01-20` | 自動更新推奨 |
| 成約日 | date | ❌ | 成約した日付 | `2024-03-15` | 成約時のみ |
| 失注理由 | string | ❌ | 失注した場合の理由 | `予算不足` | |
| 備考 | string | ❌ | 自由記述のメモ | `競合他社との比較検討中` | |

**商談ステージの選択肢**（カンバン表示に対応）:
- `見込み`: リード獲得直後
- `商談中`: ヒアリング・要件定義中
- `提案中`: 提案書提出済み
- `成約`: 契約締結済み
- `失注`: 成約に至らなかった

**ステージの遷移ルール**:
- 基本的に左から右へ進む（見込み → 商談中 → 提案中 → 成約）
- どのステージからでも「失注」に移動可能
- 「成約」または「失注」になったら基本的に移動しない

#### 2.2.3 活動履歴（activities）

| カラム名 | 型 | 必須 | 説明 | 例 | 備考 |
|---------|-----|------|------|-----|------|
| 活動ID | string | ✅ | 一意の識別子（自動生成推奨） | `ACT-001` | |
| 顧客ID | string | ✅ | 顧客マスタの顧客ID | `CUST-001` | 外部キー |
| 活動日時 | datetime | ✅ | 活動が行われた日時 | `2024-01-15 14:30` | 時分まで記録 |
| 活動種別 | string | ✅ | 活動の種類 | `電話` | 選択肢必須（後述） |
| 活動タイトル | string | ✅ | 活動のタイトル | `初回ヒアリング` | |
| 活動内容 | string | ❌ | 活動の詳細内容 | `システム要件について説明` | 長文可 |
| 担当者 | string | ❌ | 活動を行った担当者名 | `佐藤花子` | |
| 次回アクション | string | ❌ | 次回の予定アクション | `提案書を送付` | |
| 次回アクション日 | date | ❌ | 次回アクション予定日 | `2024-01-20` | |
| 重要度 | string | ❌ | 活動の重要度 | `高` | 選択肢（高/中/低） |

**活動種別の選択肢**:
- `電話`: 電話での連絡
- `メール`: メール送信
- `訪問`: 訪問・面談
- `会議`: オンライン/オフライン会議
- `提案`: 提案書提出
- `見積`: 見積書提出
- `その他`: 上記以外

**活動履歴の活用方法**:
- 顧客詳細画面で時系列表示（タイムライン）
- 最終接触日の自動更新（最新の活動日時を顧客マスタに反映）
- 次回アクションのリマインダー機能（未実装でもデータとして保持）

### 2.3 データ整合性ルール

1. **外部キー制約**:
   - `deals.顧客ID` は `customers.顧客ID` に存在すること
   - `activities.顧客ID` は `customers.顧客ID` に存在すること

2. **必須項目のバリデーション**:
   - 顧客マスタ: 顧客ID、顧客名、会社名、顧客ステータス、登録日
   - 商談管理: 商談ID、顧客ID、商談名、商談金額、商談ステージ、開始日、更新日
   - 活動履歴: 活動ID、顧客ID、活動日時、活動種別、活動タイトル

3. **データ型の制約**:
   - 日付型: `YYYY-MM-DD` 形式
   - 日時型: `YYYY-MM-DD HH:MM` 形式
   - 数値型: 0以上の数値（金額は整数、見込み度は0-100）
   - メールアドレス: 基本的なメール形式のバリデーション

## 3. デザイン仕様

### 3.1 UI構造の要件

#### 3.1.1 ページ構成（4ページ）

**1. ダッシュボード（/）**
- **目的**: 全体の状況を一目で把握
- **レイアウト**: グリッド（12カラム）
- **コンポーネント**:
  - KPIカード × 4（総顧客数、今月の新規リード、対応中の商談数、本日の要対応タスク）
  - グラフ × 2-3（顧客ステータス分布、商談ステージ分布、売上推移）
  - 最近の活動履歴一覧（テーブル形式、最大10件）

**2. 顧客一覧（/customers）**
- **目的**: 顧客の検索・一覧表示
- **レイアウト**: リスト
- **コンポーネント**:
  - 検索バー（顧客名、会社名で検索）
  - フィルター（顧客ステータス、見込み度、担当者）
  - 顧客一覧テーブル（ソート・ページネーション対応）
  - 新規顧客登録ボタン

**3. 商談パイプライン（/pipeline）**
- **目的**: 商談の進捗をカンバン形式で可視化
- **レイアウト**: カンバン（横スクロール）
- **コンポーネント**:
  - カンバンボード（見込み、商談中、提案中、成約、失注の5列）
  - 各カードに表示: 顧客名、会社名、商談金額、見込み度、担当者
  - ドラッグ&ドロップでステージ移動（未実装でもデータ構造は対応）

**4. 顧客詳細（/customers/:id）**
- **目的**: 個別顧客の詳細情報と関連データを表示
- **レイアウト**: 2カラム（左: 顧客情報フォーム、右: 活動履歴タイムライン）
- **コンポーネント**:
  - 顧客情報フォーム（編集可能）
  - 関連商談一覧（テーブル形式）
  - 活動履歴タイムライン（時系列表示）
  - 新規活動登録ボタン

#### 3.1.2 テーマ設定

```json
{
  "theme": {
    "primaryColor": "#8b5cf6",
    "secondaryColor": "#6366f1",
    "fontFamily": "Inter, -apple-system, BlinkMacSystemFont, 'Segoe UI', sans-serif",
    "borderRadius": "8px",
    "darkMode": true,
    "spacing": {
      "small": "8px",
      "medium": "16px",
      "large": "24px"
    }
  }
}
```

**カラーパレット**:
- プライマリ: `#8b5cf6` (紫) - アクションボタン、リンク
- セカンダリ: `#6366f1` (インディゴ) - サブアクション
- 成功: `#10b981` (緑) - 成約、完了
- 警告: `#f59e0b` (オレンジ) - 注意が必要な項目
- エラー: `#ef4444` (赤) - 失注、エラー
- グレー: `#6b7280` (グレー) - 非アクティブ

#### 3.1.3 コンポーネント仕様

**KPIカード**:
- アイコン + 数値 + ラベル
- 前月比の増減表示（可能であれば）
- ホバー時に詳細情報を表示

**テーブル**:
- ヘッダー固定（スクロール時も見える）
- ソート機能（クリックで昇順/降順切り替え）
- ページネーション（20件/ページ推奨）
- 行選択機能（複数選択可）

**カンバンボード**:
- 各列は固定幅（300px程度）
- カードは影付きで浮き上がる見た目
- カード内に商談金額を大きく表示
- 見込み度をバッジで表示（高=緑、中=黄、低=グレー）

**タイムライン**:
- 時系列で上から下へ表示（最新が上）
- 各活動をカード形式で表示
- 活動種別をアイコンで区別
- 日付でグループ化（「今日」「昨日」「今週」「先週」「それ以前」）

**フォーム**:
- ラベル + 入力フィールドの縦並び
- 必須項目は `*` マーク
- エラーメッセージは入力フィールドの下に表示
- 保存ボタンは右下に固定

### 3.2 レスポンシブデザイン

- **デスクトップ（1024px以上）**: フルレイアウト
- **タブレット（768px-1023px）**: 2カラム → 1カラムに変更
- **モバイル（767px以下）**: すべて1カラム、カンバンは縦スクロール

### 3.3 アクセシビリティ

- キーボードナビゲーション対応
- コントラスト比 WCAG AA 準拠
- フォーカスインジケーターの明確化

## 4. サンプルデータ仕様

### 4.1 データ量の要件

- **顧客マスタ**: 最低 **20件**（推奨: 30-50件）
- **商談管理**: 最低 **15件**（推奨: 25-40件）
- **活動履歴**: 最低 **50件**（推奨: 80-120件）

**理由**:
- ダッシュボードのグラフが意味を持つ量
- 検索・フィルター機能のテストができる量
- 実際の業務で使う初期データ量に近い

### 4.2 データのリアリティ要件

#### 4.2.1 顧客マスタのサンプルデータ要件

1. **多様性**:
   - 顧客ステータス: 見込み、商談中、既存顧客、休眠、失注をバランスよく
   - 見込み度: 高、中、低をバランスよく
   - 業種: IT、製造、小売、サービスなど多様に
   - 規模: 小規模（10人以下）から大規模（1000人以上）まで

2. **リアリティ**:
   - 会社名: 実際に存在しそうな名前（「株式会社○○」「○○商事」など）
   - メールアドレス: 実際のドメイン形式（`@example.com` ではなく `@company.co.jp` など）
   - 電話番号: 実際の形式（`03-1234-5678`、`090-1234-5678` など）
   - 住所: 実際の都道府県・市区町村名を使用

3. **関連性**:
   - 同じ会社名の顧客が複数存在する場合、部署名・役職で区別
   - 担当者が複数の顧客を担当している関係性

#### 4.2.2 商談管理のサンプルデータ要件

1. **ステージ分布**:
   - 見込み: 3-5件
   - 商談中: 4-6件
   - 提案中: 3-5件
   - 成約: 2-4件
   - 失注: 1-3件

2. **金額の幅**:
   - 小規模: 50万円 - 200万円
   - 中規模: 200万円 - 1000万円
   - 大規模: 1000万円 - 5000万円
   - 平均的な商談金額: 300万円 - 800万円

3. **時系列の整合性**:
   - 開始日は過去3ヶ月以内に分散
   - 成約日は開始日より後
   - 更新日は開始日以降、成約日以前（成約していない場合は最新日付）

4. **顧客との紐付け**:
   - 1顧客に対して1-3件の商談が存在
   - 既存顧客には成約済み商談が存在
   - 見込み客には進行中の商談が存在

#### 4.2.3 活動履歴のサンプルデータ要件

1. **活動種別の分布**:
   - 電話: 30-40%
   - メール: 20-30%
   - 訪問: 15-20%
   - 会議: 10-15%
   - 提案・見積: 5-10%
   - その他: 5%以下

2. **時系列の分布**:
   - 今日: 3-5件
   - 昨日: 2-4件
   - 今週: 10-15件
   - 先週: 15-20件
   - それ以前: 残り

3. **顧客との紐付け**:
   - 1顧客に対して2-8件の活動履歴
   - 既存顧客・商談中の顧客には活動履歴が多い
   - 休眠顧客には最終接触日が古い活動履歴のみ

4. **内容のリアリティ**:
   - 活動タイトル: 「初回ヒアリング」「要件確認」「提案書送付」など具体的に
   - 活動内容: 簡潔だが具体的な内容（「システム要件について説明。来月に提案書を提出予定」など）
   - 次回アクション: 具体的なアクション項目（「提案書を送付」「見積書を提出」「訪問予定を調整」など）

**生成時の注意点**:
- 顧客IDは必ずcustomersに存在するIDを使用
- 商談ステージと見込み度は整合性を持たせる（提案中 → 見込み度70%、成約 → 見込み度100%）
- 成約済みの商談には成約日を設定
- 失注の商談には失注理由を設定

#### 4.3.3 活動履歴生成例

```javascript
// 50件の活動履歴データ生成例
const activities = [
  {
    活動ID: 'ACT-001',
    顧客ID: 'CUST-001', // customersの顧客IDと紐付け
    活動日時: '2024-01-15 14:30',
    活動種別: '訪問',
    活動タイトル: '初回ヒアリング',
    活動内容: 'システム要件について説明。現在の課題と要望をヒアリング。',
    担当者: '佐藤花子',
    次回アクション: '提案書を送付',
    次回アクション日: '2024-01-20',
    重要度: '高'
  },
  // ... 49件追加
]
```

**生成時の注意点**:
- 顧客IDは必ずcustomersに存在するIDを使用
- 活動日時は時系列順に並ぶ（最新が上）
- 同じ顧客に対して複数の活動履歴を生成（2-8件程度）
- 活動種別はバランスよく分布
- 次回アクションは具体的に記述

### 4.4 データの整合性チェック

サンプルデータ生成後、以下の整合性をチェック：

1. **外部キー整合性**:
   - `deals.顧客ID` がすべて `customers.顧客ID` に存在するか
   - `activities.顧客ID` がすべて `customers.顧客ID` に存在するか

2. **時系列整合性**:
   - 商談の開始日 < 更新日 < 成約日（成約している場合）
   - 活動履歴の活動日時が時系列順になっているか
   - 顧客の最終接触日が、その顧客の活動履歴の最新日時と一致しているか

3. **ステータス整合性**:
   - 商談ステージが「成約」の顧客は、顧客ステータスが「既存顧客」になっているか
   - 商談ステージが「失注」の顧客は、顧客ステータスが「失注」になっているか（または見込み度が低いか）
